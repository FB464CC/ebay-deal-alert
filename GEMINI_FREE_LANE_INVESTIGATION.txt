Code-path finding: the free Gemini lane DOES run after the paid cap is exhausted
- PASS 3 grants an AI-check slot first. The ordinary shared counter is named gemini_calls, but it counts admitted photo checks regardless of which provider ultimately serves them. Isolated scrape and Scout candidates use their own small counters; one ending-soon auction can use a reserved extra slot.
- A granted candidate calls check_photos_with_gemini(), which downloads images and calls _call_photo_check().
- AI_PHOTO_PROVIDER="deepseek" makes _call_photo_check() try _call_deepseek_json() first.
- _call_deepseek_json() alone calls _reserve_paid_ai_spend(). At the exhausted $10 cap, reservation returns False and _call_deepseek_json() returns None without a DeepSeek network call.
- The router treats that None as primary-provider failure and immediately calls _call_gemini_json().
- _call_gemini_json() reads GEMINI_API_KEY and GEMINI_MODEL, then POSTs directly to the Google Generative Language API. It contains no paid-ledger/budget check. Therefore NO_AI_BUDGET / MONTHLY_BUDGET_EXHAUSTED is not a pre-Gemini short circuit.
- _PAID_AI_BUDGET_EXHAUSTION is only consulted after the photo-check attempt. If Gemini returned usable JSON, the result is merged and ai_checked becomes true. If no provider returned a usable result, the retryable gate reason is relabeled MONTHLY_BUDGET_EXHAUSTED. This label describes why the configured paid primary was unavailable; it does not block the free fallback.

Multiple-key/project policy finding
- Multiple keys in the SAME project do not multiply quota. Google explicitly says: "Rate limits are applied per project, not per API key." Source: https://ai.google.dev/gemini-api/docs/rate-limits
- Each API key belongs to a Cloud project. Source: https://ai.google.dev/gemini-api/docs/api-key
- Separate-project sharding can therefore work technically because the enforcement unit is a project. But doing that specifically to multiply this one bot's documented free quota is not a permitted workaround.
- The Gemini Additional Terms (effective 2026-03-23) incorporate the Google APIs Terms: https://ai.google.dev/gemini-api/terms
- Google APIs Terms section 2(d) says exactly: "You agree to, and will not attempt to circumvent, such limitations documented with each API." It then requires Google's express consent for use beyond the limits. Source: https://developers.google.com/terms
- Enforcement is real, not merely theoretical. Section 3(a) says Google may suspend API access without notice when it reasonably believes the Terms were violated; section 8(a) reserves termination/discontinuation rights. Intentionally creating extra accounts/projects to shard this single workload after its 500 RPD cap is reached squarely fits the ordinary meaning of circumventing a documented limitation.
- Plain conclusion: same-project key rotation adds zero quota; cross-project/account pooling would add technical throughput but is a ToS/ban-risk method, not a clean free tier. Losing/suspending the currently productive project would sacrifice today's working fallback lane and its observed delivered alerts.

At the observed 567/day peak, N=1 would make aggregate nominal capacity 1,000/day and fully cover current photo-request volume, leaving 433/day unused. More than one adds no realistic benefit at current volume. This is precisely the sharding pattern Google section 2(d) says not to use to circumvent documented limits, so it is not recommended or represented as a compliant plan.

Implemented generic credential-pool infrastructure (no secrets or accounts)
- ebay_deal_alert.py accepts GEMINI_API_KEYS and the backward-compatible GEMINI_API_KEY; either may contain comma/newline-separated credentials. Duplicates and blank entries are removed. Because the existing Actions workflow already passes GEMINI_API_KEY, a future user decision can supply a list without any workflow edit.
- Calls begin round-robin across configured slots. A 429 marks only that slot unavailable for the remainder of the short-lived process and immediately tries the next slot within the original timeout deadline. A new scheduled process probes again, allowing an RPM window to recover.
- Each slot has independent process-local attempts/successes/rate_limited/available telemetry. It is intentionally described as credential health, not independent quota: keys in one project share Google's project-level counters.
- Key material remains environment-only. It is never placed in config.json, logs, reports, committed state, or usage snapshots. Gemini authentication moved from a URL query parameter to the x-goog-api-key request header, preventing HTTP exception text from exposing a key.
- No real key/account/project was created, read, copied, stored, or modified. No paid-budget/accounting or saved-search field was touched. GEMINI_CALL_LIMIT remains 12 because live evidence rejects an increase.
- Added four focused regression tests for parsing/deduplication, round-robin order and header-only authentication, 429 fall-through with independent usage, and all-slots-limited behavior. Focused result: 26 passed in 1.38s.
