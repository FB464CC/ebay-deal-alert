## HIGH — Loro Piana / Brunello Cucinelli bar permanently blocks every candidate before its first AI check

**File+line:** `ebay_deal_alert.py:2030-2032` (bar) interacting with `:3489-3496` (pre_ai_block early-skip).

The bar is:

```python
if "loro piana" in search_query_lower or "cucinelli" in search_query_lower:
    if deal_rating != "Steal":
        return f"loro piana/cucinelli bar: deal_rating '{deal_rating}' below Steal"
```

`deal_rating` is `None` until the AI check runs in PASS 3 — it is set nowhere before that (`score_listing()` returns no price fields; the only setters are `compute_deal_rating()` at `:3653`/`:3705`, both *after* the pre-skip). So on every candidate's first run `deal_rating is None`, and `None != "Steal"` is True, so the bar returns `"loro piana/cucinelli bar: deal_rating 'None' below Steal"`.

That string does **not** contain the `"no AI price"` substring. The pre-skip at `:3489-3496` therefore treats it as a permanent block:

```python
pre_ai_block = is_blocked_by_steal_quality_gate(result, category=category)
if pre_ai_block and "no AI price" not in pre_ai_block:
    ...
    mark_seen(conn, item_id, fingerprint, total_price)
    continue
```

**Failure scenario:** a new "loro piana" or "brunello cucinelli" listing (both grab_on_sight, both explicitly requested "wider coverage" brands per `:2019-2029`) is scored in PASS 1 with `deal_rating=None`, enters PASS 3, and is immediately `mark_seen`'d as permanently blocked — *before an AI photo/price check ever runs*. It never gets a retry (no `ai_pending` row, and it's in the `seen` table). Every Loro Piana/Cucinelli candidate is discarded on its first run; these two searches can never alert again.

Contract violation in the exact direction the spec flags: an **AI-resolvable block that wrongly lacks** `"no AI price"`. Compare the gamecocks bar (`:2011-2012`) and crown-crafted bar (`:2061-2062`), which both correctly guard `deal_rating is None` first and return the `"no AI price estimate..."` retry marker.

## HIGH — Knitwear bar has the same defect: grab_on_sight knitwear permanently blocked before AI

**File+line:** `ebay_deal_alert.py:2071-2075` interacting with `:3489-3496`.

```python
if category == "knitwear":
    if brand_tier != "grab_on_sight":
        return "knitwear bar: brand not grab_on_sight-tier (...)"
    if deal_rating != "Steal":
        return f"knitwear bar: deal_rating '{deal_rating}' below Steal - only grail-or-better on sweaters"
```

For a grab_on_sight-tier knitwear candidate (e.g. Johnstons of Elgin cashmere — grab_on_sight per config — surfacing on a sweater/cashmere search), `brand_tier == "grab_on_sight"` passes the first check, then `deal_rating is None` makes `deal_rating != "Steal"` True, returning a `"...below Steal..."` string with no `"no AI price"`. The pre-skip marks it `seen` permanently.

**Failure scenario:** a Johnstons of Elgin / Loro Piana cashmere sweater (the exact "grab_on_sight grail" this gate was built to allow per `:1924-1933`) is killed on first sight before any AI vetting, and never retried. This contradicts the bar's own docstring, which requires "grab_on_sight-tier brand AND a real AI-confirmed Steal rating" — a candidate that *would* earn Steal never gets the chance to be checked. Same contract violation as the loro piana bar: the `deal_rating != "Steal"` test must be guarded by `if deal_rating is None: return "knitwear bar: no AI price estimate ..."` first.

(Same root cause as finding 1 — one guard per bar, or better, a shared "no price signal yet" early return.)

## MEDIUM — Backlog grows without bound; aging table converts "starved forever" into "deferred for hours"

**File+line:** `_ai_check_priority()` `:3384-3463`, `mark_ai_pending()` `:949-965`, `get_ai_pending_minutes()` `:926-946`, `GEMINI_CALL_LIMIT=3` `:248`.

The spec's load is "dozens of candidates per run, most needing AI." Service rate is 3 AI calls/run. The aging table (`ai_pending`, FIFO-by-`first_seen_at`) guarantees **eventual** service for any stuck candidate — the permanent-starvation bug (Brooks Brothers 57 rounds, `:3368-3377`) is genuinely fixed. It does **not** bound latency:

- If `N > 3` new candidates need AI per run (realistic — the file itself says Vinted alone surfaces 5–6.5k listings/run at `:3778`), backlog grows by `N-3` per run, monotonically.
- A fresh real steal lands at the back of the queue and waits `backlog_depth / 3` runs. At ~30 new/run: after 1h the backlog is ~324 deep, and a new arrival waits ~108 runs ≈ 9 hours.

So a genuine steal can still be deferred effectively-indefinitely, on a market where (per the file's own rationale at `:3376-3377`) a real steal sells out in minutes. The change made this structural rather than incidental: previously grab_on_sight candidates in normal categories blind-trusted through *without consuming an AI slot* (`:3355-3363`); now **every** alerting path consumes one of the 3 slots, so AI demand ~tripled against an unchanged supply. This is the intended "vet everything" tradeoff (explicit user instruction, `:3744-3747`), but the aging table's original promise — "alerts within minutes" — is no longer achievable under the stated load; it only makes the queue fair, not short.

## LOW — `_ai_check_priority()` sort key contradicts its own comment (currently inert)

**File+line:** `ebay_deal_alert.py:3388-3403` (comment) vs `:3459` (sort key).

The comment says to rank "by how close a candidate is to actually alerting," closest first, and warns against burying the one-check-from-alerting candidates (`:3388-3393`). But:

```python
one_check_from_alerting = (no_ai_block is None) or ("no AI price" in no_ai_block)
must_have_ai = not one_check_from_alerting
...
0 if must_have_ai else 1,   # :3459
```

`must_have_ai=True` now means *permanently blocked* (gate returns a non-"no AI price" reason), and those sort **first** (key 0), while the one-check-from-alerting candidates sort **last** (key 1) — the opposite of the stated intent.

It is inert today only because the `pre_ai_block` skip (`:3489-3496`) consumes no budget for the permanently-blocked candidates before the one-check group is reached, so the 3 AI slots still flow to the one-check group in age/price order. It's a trap waiting: the variable name `must_have_ai` no longer means "needs AI," and if the pre-skip is ever removed or reordered, the sort would burn the budget on permanently-blocked candidates first. Recommend either flipping the key to `1 if must_have_ai else 0` to match the comment, or fixing the comment/name.
