Checkpoint 2 - live-log transition map
--------------------------------------
- Re-derived the reported Vinted number from run 34392932307 (created
  19:05 UTC): final prefetch count was exactly 2,711. All observed Vinted
  catalog calls in that run were HTTP 200; the run hit the 90-second
  marketplace deadline and late Vinted workers were discarded. This is a
  throughput collapse, not a JSON-shape failure or a Vinted HTTP outage.
- Vinted is cyclic rather than continuously degraded. Examples from the live
  logs: 7,114 listings at 18:25, 2,711 at 19:05, 5,103 at 19:35, roughly
  1,100-1,460 from 19:55 through 20:15, 7,097 at 20:20, and 5,727 at
  21:10. The persisted state shows why: Vinted repeatedly reaches the generic
  32x pacing multiplier (0.15s becomes 4.8s between starts), that multiplier
  has no success-driven decay, and it falls off only at a fixed 30-minute
  expiry cliff. Healthy bursts produce 429s, then several subsequent runs are
  deliberately throttled until the cliff expires.
- This Vinted pacing also exposes a shared scheduling bug: one flat queue is
  serviced by eight generic workers. A worker sleeping inside Vinted's global
  pacer still occupies a generic worker, so enough slow Vinted tasks can
  consume the pool and starve Poshmark/ShopGoodwill tasks behind them. Many
  affected runs log `Marketplace prefetch hit its hard deadline` and discard
  late workers.
- Re-derived ShopGoodwill's alert window in run 34392932307: four cURL error
  28 failures, each timing out after ~8,002 ms with zero response bytes.
  Other platforms returned data in the same run, so this is not evidence of
  runner-wide DNS/network failure. ShopGoodwill later returned HTTP 200s, but
  timeout bursts recur intermittently and worsen shared-pool starvation.
- Poshmark is intermittent, not a permanent parser break. Healthy examples in
  the inspected window include 743 listings at 19:00 and 714 at 21:10; zero
  runs have no logged 4xx/5xx, request exception, timeout, non-JSON warning,
  or traceback. The newest 21:15 run again returned zero, so it cannot yet be
  called recovered. More response metadata is needed to distinguish an HTTP
  200 empty-body/shadow-throttle from deadline truncation in each zero run.
- Grailed and Depop stayed essentially flat at 105 and ~372-373 listings
  while the three target platforms fluctuated. That is evidence against a
  broad GitHub Actions runner/DNS outage and against a shared parser-library
  regression affecting every outbound marketplace.

  20260907.300. Both builds produced healthy and degraded Poshmark/Vinted
  runs; e.g. 20260907 produced both the 20:15 degraded run and the 20:20
  fully recovered run. Runner image generation is not the cause.
- The relevant repo regression predates today's alert: commit f97690fa
  (2026-09-07) persisted the generic adaptive multiplier for OfferUp, but
  Vinted also calls that generic rate-limit function. The implementation
  reloads a fresh 429-driven multiplier for up to 30 minutes with no
  success-driven decrease, producing the measured sawtooth once Vinted gets
  a burst of 429s. It also rewrites every platform's persisted timestamp
  whenever any one platform changes, so one platform can accidentally keep
  another platform's stale slowdown fresh.
- The Poshmark zero is therefore not evidence of 33 successful HTTP-empty
  responses. Request telemetry increments when a task is dequeued, before
  the adapter call. During the 10-second deadline margin, workers can drain
  queued tasks through _fetch_marketplace's immediate deadline return and
  count them as requests that never touched Poshmark. Matching task rotations
  return hundreds of Poshmark rows after Vinted's backoff expires and zero
  while a fresh 32x Vinted multiplier monopolizes the shared workers. A
  permanent JSON field rename is ruled out; successful-response shape logging
  is still being added so a future server-side empty/malformed response can be
  proven directly rather than inferred.

Checkpoint 4 - fixes and validation
-----------------------------------
- Root-cause synthesis: there is no credible single external outage across
  all four marketplaces. Vinted and Poshmark share an internal orchestration
  failure: Vinted's persisted generic backoff stayed at 32x despite successful
  responses, and its sleeping work occupied the flat shared pool before the
  rotated queue reached Poshmark. ShopGoodwill's four cURL(28) events were an
  independent transient proxy/TLS-path timeout burst, although the old shared
  pool let those stalls amplify deadline starvation. The fenced eBay scrape
  lane's Akamai 403 is independent again.
- Backoff state now preserves a separate update timestamp per platform, so an
  OfferUp 429 cannot refresh Vinted's expiry. Eight consecutive successfully
  parsed responses halve the affected platform's multiplier one rung at a
  time (32 -> 16 -> 8 -> 4 -> 2 -> 1); partial success streaks persist across
  five-minute workflow processes without extending the multiplier timestamp.
  Every generic-backoff response path registers clean responses, and corrupt,
  non-finite, non-positive, or future-dated state entries are ignored.
- Marketplace dispatch now has a small private worker lane per platform.
  Workers stop dequeuing at the real fetch deadline; the following margin is
  only for collecting already-started bounded calls. A sleeping Vinted pacer
  or stalled ShopGoodwill request can therefore no longer consume Poshmark's
  execution slots.
- Health telemetry now records scheduled, actually started, and completed
  requests separately. Deadline-incomplete samples are excluded from the
  per-request baseline and report coverage loss rather than a false parser or
  count-collapse diagnosis. OfferUp/Depop batch results carry equivalent
  per-query progress metadata, including partial deadline returns. Their
  request timeout is recomputed after adaptive pacing, so pacing that consumes
  the budget cannot launch or count a network call after the deadline.
- Vinted/ShopGoodwill circuit-breaker cooldowns are checked before dequeueing
  more work and recorded explicitly, including a breaker tripped by the final
  request. Cooldown rows and all other incomplete-coverage rows are excluded
  from future baselines; their alert says cooldown/coverage rather than
  claiming completed HTTP-empty responses or a parser collapse.
- Poshmark successful JSON now logs distinct safe diagnostics for a wrong
  top-level type, missing/wrong `data` shape, a valid empty list, and a
  nonempty list from which zero rows normalize. The row-level signal reports
  structural field counts, bounded key names, numeric-safe totals, and metadata
  types only, not listing or trace values. This does not claim today's zero was
  a shape change; it closes the exact observability gap that prevented the old
  production logs from proving or excluding one.
- ShopGoodwill retains its existing single retry and timeout. Evidence did
  not support retrying harder or widening timeouts. Failure logs now include
  attempt number, elapsed time, and only a yes/no proxy-configured marker so a
  future recurrence can distinguish connection stalls without exposing proxy
  credentials.
- Production run 34408622902 (created 21:45 UTC) was still on the old
  undeployed code and still degraded: Vinted returned 1,322 listings from 30
  observed successful catalog calls, Poshmark produced no collected result or
  success diagnostic under the old observability, and the marketplace
  deadline fired. ShopGoodwill made 26 logical HTTP-200 calls with no timeout
  warning, confirming transport recovery. The fenced eBay scrape lane emitted
  15 Akamai HTTP-403 warnings.
- Exact local validation from this checkout:
