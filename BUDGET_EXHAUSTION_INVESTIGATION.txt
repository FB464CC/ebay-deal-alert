Accounting durability and real demand
- End-of-day Git snapshots expose a more serious accounting defect. September's
  ledger was $2.839 / 695 reservations on Sep 1, then after the Sep 4 history
  rewrite/reconciliation it was only $0.605 / 153. It subsequently grew to
  $3.770 / 846 (Sep 5), $5.227 / 1,199 (Sep 6), $7.134 / 1,622 (Sep 7), and
  $10.000 / 2,232 (Sep 8). The dedicated file therefore lost a prior $2.839
  monthly balance; the actual sequence contains at least 2,927 reservations
  totaling $12.839 (2,478 vision + 449 text), even though the current ledger
  reports only $10/2,232. This is not double-counting. It is a fail-open rollback
  that made the nominal $10 guard permit more provider work than intended.
- From the post-reset Sep 4 snapshot through exhaustion, reservations grew about
  $9.395 in roughly 3.95 days: about $2.38 reserved/day or $71/month at unchanged
  demand. The $10 pool therefore represented only about 4.2 days of current
  throughput, matching the observed Sep 4-to-Sep 8 lifetime.
- At current volume, $10/month can sustain roughly 22% of the reservation demand
  (`10 / 71`). Merely redistributing the per-run slots cannot change that.

Provider/billing audit
- Current code checks the DeepSeek key, reserves exactly once, then makes exactly
  one HTTP request. The photo router does not retry DeepSeek: on None/error it
  falls back to Gemini. Text second-opinion and pre-alert sanity calls each make
  their own separately priced $0.001 reservation. No code path bills the same
  DeepSeek HTTP attempt twice.
- Reservations currently remain charged on timeouts, HTTP errors, malformed JSON,
  and unusable output by deliberate fail-closed design. Real sampled pre-cap logs
  do show this class of conservative waste: run 34283616996 had one DeepSeek read
  timeout; run 34284924343 had two; run 34285369560 had one before reaching the
  cap. Whether a timed-out server-side completion was actually billed cannot be
  proven from the client log, so refunding failed attempts would be speculative
  and unsafe. Successful responses, however, include authoritative token usage
  and can be safely settled downward from a conservative reservation.
- Fresh official DeepSeek documentation says the configured legacy model name is
  still accepted but now routes to `deepseek-flash` (V4.1 Flash) at the same Flash
  pricing. Images are billed as input tokens, independently per image, with up to
  1,024 tokens/image; this bot sends at most eight. Current peak prices are
  $0.30/million cache-miss input tokens and $1.20/million output tokens (off-peak
  is half; cache hits are cheaper). The API response exposes prompt/cache-miss/
  cache-hit/completion token counts and explicitly calls returned usage the source
  of truth.
- A concrete efficiency bug exists after the model rollover: current DeepSeek
  requests omit the `thinking` control, while current official docs say thinking
  is enabled by default at high effort. These calls ask for compact deterministic
  JSON classification, so paying for hidden reasoning output is avoidable. The
  implementation will explicitly disable thinking, cap JSON output, and settle
  each successful reservation to a conservative PEAK-rate calculation from the
  provider's own returned usage. Failed/unknown-usage calls will keep the full
  reservation. This reduces ledger consumption without assuming free failures or
  increasing the $10 cap.

Implemented remediation
- AI_PAID_MONTHLY_BUDGET_USD remains exactly $10. No code or configuration change
  increases the monthly dollar ceiling. The larger $0.010 vision and $0.002 text
  figures are pre-request safety ceilings, not assumed per-call charges: every
  successful response is now settled down from authoritative token usage at the
  documented PEAK cache-miss input/output rates. Missing usage, timeouts, HTTP
  errors, and malformed responses retain the entire reservation. Output is capped
  at 2,048 vision / 512 text tokens and DeepSeek thinking is explicitly disabled.
- Added monotonic aggregate accounting (`gross_reserved_usd` and
  `settled_credit_usd`) while preserving the existing `ai_paid_spend` compatibility
  table. The accounting is mirrored into the existing cache-backed SQLite state
  and component-wise reconciled before reservation. This prevents the observed
  whole-file rollback from lowering either cumulative component, without adding
  a per-call table that would rapidly bloat the git-backed database.
- Added a durable, once-per-(UTC month, configured cap) ntfy notification titled
  `[AI BUDGET EXHAUSTED]`. It says the outage is system-wide, states effective
  spend/cap and the UTC reset date, and explains that Gemini fallback may still
  be quota-limited. The notification claim is mirrored; a failed ntfy request
  releases the claim so a later run retries instead of suppressing the warning.
- Alert-log schema v4 now writes `MONTHLY_BUDGET_EXHAUSTED` plus the effective
  balance, cap, and reset timestamp. This is distinct from ordinary
  `NO_AI_BUDGET` per-run pacing. These candidates remain retryable rather than
  being permanently marked seen. The weekly digest now prints an explicit
  `AI monthly budget: EXHAUSTED` line with the reset date.
- Gemini fallback behavior is deliberately preserved: production evidence shows
  it can still deliver sporadically after DeepSeek is capped. No speculative
  refund for ambiguous failed HTTP requests, no unproven batching change, and no
  new candidate-filter heuristic was introduced.

Decision-grade capacity conclusion
- The prior flat-reservation data implies roughly $71/month of nominal demand,
  whereas the configured decision is $10/month. The implemented usage settlement
  and disabled thinking remove real accounting/provider waste, but production
  usage telemetry under the new code is required to quantify the new steady-state
  monthly cost honestly. The current September legacy balance is not retroactively
  credited because historical token usage is unavailable. If live settled usage
  still follows the old rate, sustaining all prior demand would require about
  $71/month; sustaining it at $10 would require about a 78% reduction in paid-call
  demand. Raising the cap remains a user decision and was not done here.
