2026-09-09 - Dependency, proxy-failure, and request-fingerprint findings.
- The fresh Actions log installs Scrapling 0.4.15 and curl_cffi 0.16.3. The local environment resolves the same exact versions. `requirements.txt` constrains Scrapling to `>=0.4.15,<1`; 0.4.15 is also the current/latest Scrapling release (published 2026-08-23): https://github.com/D4Vinci/Scrapling/releases/tag/v0.4.15
- Installed 0.4.15 source (`scrapling/engines/static.py`) shows plain `Fetcher` defaults to `impersonate="chrome"` and `stealthy_headers=True`. curl_cffi supplies the browser fingerprint/header set; Scrapling adds a Google referrer. Thus the outage is not explained by a lone/static User-Agent: the existing lane already uses HTTP-level Chrome impersonation.
- A local loopback capture of the unmodified Fetcher request showed Chrome 150 client hints/User-Agent and complete navigation headers (Accept, Accept-Language, Accept-Encoding, Sec-Fetch-*). It also exposed a concrete inconsistency: curl_cffi generated `Sec-Fetch-Site: none` while Scrapling separately added `referer: https://www.google.com/`. A real navigation carrying a cross-origin Google referrer should say `Sec-Fetch-Site: cross-site`; `none` denotes a user-originated navigation with no referring origin. This mismatch is a credible fingerprinting signal and is the evidence for explicitly constructing internally consistent navigation headers.
- One courtesy baseline call from this machine using the current/unmodified Fetcher against the real eBay search URL returned HTTP 403. Selected response metadata: final host `www.ebay.com`, `Server: AkamaiGHost`, `Content-Type: text/html`, body length 1,987 bytes. This is independent evidence that eBay/Akamai is currently denying this HTTP fingerprint/path even outside Actions; no proxy was used locally.
- An unreachable proxy (`http://127.0.0.1:1`) produced curl_cffi `ProxyError`/curl code 7 after Scrapling retries and was caught by `search_ebay_scraped`, so it did not masquerade as an HTTP 403. A syntactically malformed value (`not-a-proxy-url`) was nevertheless accepted by the current code/curl layer as a hostname and ultimately raised `curl_cffi.requests.exceptions.Timeout`. Current application logging omits the exception type and route, and there is no up-front proxy URL validation.
- Scrapling 0.4.15 does expose `StealthyFetcher`, but installed source and official v0.4.15 docs show it is a full Patchright/Chromium browser fetcher. Official installation requires `scrapling install` to download browsers/system dependencies; this workflow only runs `pip install -r requirements.txt`. Switching imports alone would therefore fail on the fresh runner, and launching a browser per sequential search would materially increase cost. It is not a viable scoped fix here. Source/docs checked at https://github.com/D4Vinci/Scrapling/blob/v0.4.15/docs/fetching/stealthy.md and https://github.com/D4Vinci/Scrapling/blob/v0.4.15/README.md

2026-09-09 - Longitudinal production evidence and root-cause boundary.
- While investigating, newer run 34402919895 completed with 15 HTTP 403s and one successful scrape call returning 2 parsed listings. A 17:40Z run similarly had 15 403s and one success returning 5 listings; sampled 18:40Z and 19:40Z runs were 16/16 403. The outage remains severe/ongoing, but it is not literally 100% in every run.
- Sampled logs at 16:00Z (12 403, 4 successful calls/61 listings), 14:20Z (16 403), 2026-09-08 23:55Z (15 403, one success/60 listings), and 2026-09-07 23:55Z (16 403) all used the same populated proxy setting and showed no connection exceptions. Intermittent real parsed listing responses prove the configured route can connect and authenticate, so a globally malformed, unreachable, or wholly expired proxy secret is inconsistent with the evidence.
- Failures also occurred under curl_cffi 0.16.2 (for example 15/16 on 2026-09-08 and 16/16 on 2026-08-31); current 0.16.3 only contains Android/build/type and TLS-extension fixes per its official release notes (https://github.com/lexiforest/curl_cffi/releases/tag/v0.16.3). There is no evidence that the 0.16.3 update caused this outage.
- What cannot be proven without the secret or response metadata from the proxied 403s: whether Akamai/eBay is rejecting the rotating residential exit IPs/request fingerprint, or the proxy provider itself is generating some HTTP 403 responses. The sporadic successes make target-side/IP-reputation/fingerprint rejection more plausible than bad credentials, but that remains a bounded inference. New logs must capture safe response provenance fields so the next live run can settle it.

2026-09-09 - Implemented scoped hardening.
- `ebay_scrape.py` now supplies a complete, consistent top-level browser navigation header set: HTML Accept, en-US Accept-Language, supported compression, Google Referer, Upgrade-Insecure-Requests, and Sec-Fetch-Dest/Mode/Site/User. `Sec-Fetch-Site` is explicitly `cross-site`, matching the Google referrer. User-Agent and Sec-CH-UA remain under curl_cffi control so they stay aligned with its Chrome TLS fingerprint.
- The call explicitly retains `impersonate="chrome"` and uses one transport attempt (`retries=1`). There are already up to 16 independent calls per process; Scrapling's default three inner attempts made a dead static proxy consume repeated time and logged the credential-bearing proxy URL on intermediate failures. The application continues to make later query calls, which provide bounded subsequent attempts.
- Populated proxy values now receive up-front, secret-safe URL validation for scheme/hostname/port/whitespace. An invalid value logs only the reason and sends no request.
- Transport exceptions now log route, exception type, and a compact message with the full proxy URL, endpoint, host, username, and decoded/encoded password redacted. Received HTTP responses are a separate log form and include only safe provenance: final host, Server, Via, Proxy-Status, Content-Type, selected x-ebay fields, and body byte count. HTTP 407 has an explicit proxy-authentication diagnostic. HTTP 403 remains neutrally described as a received response while using the configured proxy; the code does not pretend it can identify the origin without metadata.
- No within-run 403 circuit breaker was added. Current production evidence includes a success after 5 consecutive 403s (newest sampled run) and a success after 10 (17:40Z sample). A low threshold would discard demonstrated recoveries and real listings from this high-value lane; a threshold high enough to preserve them saves too little time to justify stateful complexity. HTTP 403 bodies are also small and return in roughly 1-3 seconds today. The one-attempt transport setting addresses the genuinely expensive dead-proxy case without suppressing later calls.
- Added regression coverage for complete/consistent header construction, explicit Chrome impersonation, one transport attempt, malformed proxy rejection without a fetch or secret leak, typed/redacted proxy transport logging, proxied HTTP 403 response provenance, and distinct HTTP 407 proxy-auth logging.
- Targeted test result: `python3 -m pytest -q test_ebay_scrape.py` -> `20 passed in 0.56s`.
