# Auction-snipe review — findings

Read-only review of the auction-snipe feature in `ebay_deal_alert.py`. All line numbers are against the current file. Severity: high / medium / low. Nothing here is a crash or a data-corruption bug; everything below is a correctness/opportunity bug, ranked by how much it costs the feature's actual job (alerting on a closing auction).

---

## 1. Medium — A time-critical auction can be deferred to a "next run" that never comes

**File/line:** `ebay_deal_alert.py:3826-3833` (alert cap early-return); also `:3765-3799` (the "no AI price" retry path).

The whole feature is built on the premise that an ending-soon auction "does not get a next run" (`:3450-3453`), yet both terminal "try again later" mechanisms assume next-run availability:

- `:3826-3833` — after each successful alert, `alerts_sent >= MAX_ALERTS_PER_RUN` triggers `conn.close(); return`, and the comment claims remaining listings "will be picked up next run." An in-window auction beyond the cap is left un-seen and un-alerted; if it closes before the next 5-min run, it is never picked up.
- `:3765-3799` — a candidate starved of the AI budget gets `mark_ai_pending` and the comment claims "A real steal is deferred by a few minutes, not lost." That is true for a fixed-price listing (it persists), false for an auction closing in <5 min.

**Concrete scenario (reachable today):** `GEMINI_CALL_LIMIT` is 3. Run at 10:00 finds 4 ending-soon auctions (A closes 10:04, B 10:05, C 10:06, D 10:12). They all sort first (`:3456`), A/B/C consume the 3 AI slots and alert; D gets `mark_ai_pending` and is not seen. Next run is 10:05 — D is still in-window (ends 10:12), so it gets its AI slot then. That case survives. But change D to close 10:04 — it's gone before 10:05 and never alerts. The failure is proportional to how many auctions land in the same run: the budget cap, not the window, is what silently drops the ones that lose the priority race.

The `MAX_ALERTS_PER_RUN` early-return is the same bug one layer up: with the current config it is latent (`GEMINI_CALL_LIMIT=3 < MAX_ALERTS_PER_RUN=8`, so alerts can't exceed 3/run), but the config is explicitly "retunable" (`:229`), and raising the AI budget above 8 makes the cap reachable and drops in-window auctions with the same silent loss.

**Fix direction:** when the cap/AI budget would defer an `is_ending_soon_auction`, don't fall through to the generic "retry next run" path — either keep processing in-window auctions past the cap (they're the time-critical ones), or `mark_seen`/log them as "closed before AI reached it" so the miss is at least diagnosable.

## 2. Medium — dedupe prefers the auction copy, which never carries sold comps, discarding the regular copy's real price evidence

**File/line:** `ebay_deal_alert.py:3342-3353` (overwrite), `:3052-3084` (comps applied per-query), `:3682-3704` (comps consumed).

`review_candidates` dedupes by `item_id` and keeps whichever copy is the ending-soon auction (`:3342-3345`). The auction copy comes from `search_ebay_ending_soon_auctions()` — a bare eBay item-summary with **no** `sold_comp_median`. Sold comps are only ever applied inside the per-search loop from a Grailed listing present in *that* search's results (`:3052-3084`). The three configured auction searches are `"watch -pocket …"`, `"cardholder"`, `"suit"` — none of which is a saved search query, so `marketplace_listings.get(query)` is empty for every auction search and the auction copy **always** has `sold_comp_median = None`.

Meanwhile the same eBay item, found via a *regular* brand search (e.g. `"hickey freeman suit"`, `"ferragamo cardholder"`), gets `sold_comp_median`/`sold_comp_count` stamped onto it from the Grailed listing in that search's results. The dedupe then throws that away.

**Concrete scenario:** a `"hickey freeman suit"` auction ends in 10 min. The regular `"hickey freeman suit"` search and the auction `"suit"` search both return it (same `itemId`). Regular copy carries `sold_comp_median=$180, sold_comp_count=8`. Auction copy carries nothing. The auction copy overwrites (`:3342-3345`). In PASS 3, `comp_median is None`, so the "sold comps override a medium/low-confidence AI estimate" branch (`:3682-3704`) can't fire. If the AI estimate is weak (the exact case comps exist to rescue), the suit gets a Marginal/failed rating and is gate-blocked — a real steal that the regular copy would have alerted on.

Watches are immune (comps are excluded for `category == "watches"` at `:3684`); suits and cardholders are not.

**Fix direction:** when overwriting with the auction copy, merge the regular copy's `sold_comp_median`/`sold_comp_count` (and other enrichments) onto the auction listing before dropping it, or prefer the auction copy only for the time-flag fields and keep the regular copy's data.

## 3. Low/Medium — the `auction-alerted:` check runs *after* the AI spend, so an already-alerted auction re-burns a scarce AI slot

**File/line:** `ebay_deal_alert.py:3813` (check) vs `:3499-3540` (AI call).

The namespaced-key check is the *only* guard against a duplicate alert once the fingerprint 95%-tolerance has been bypassed, and it sits at the very end of PASS 3 — after PASS 1 scoring, the pre-AI gate, the description fetch, and the Gemini call. An already-alerted auction that re-enters therefore consumes one of the `GEMINI_CALL_LIMIT=3` slots before being discarded.

**Concrete scenario:** run 1 alerts on auction X at bid $50 (key `auction-alerted:X` set, fingerprint best_price $50). Run 2, five minutes later, X is still in-window but a bid retraction dropped it to $45 — `$45 < $50*0.95`, so the fingerprint check at `:3145` lets it through. It re-enters `review_candidates`, sorts **first** (`:3456`), spends a Gemini call, and only then hits `:3813` and is skipped. That call displaces a fresh candidate that actually needed it. (Normally the fingerprint 95% check at `:3145` catches the price-stable case, so this only fires on a >5% price drop.)

**Fix direction:** check `auction-alerted:{item_id}` in PASS 1, right next to the `is_new` bypass at `:3113`, and `continue` there instead of in PASS 3. The key is written before any expensive work in PASS 3 today, so it's safe to consult earlier.

## 4. Low — an ending-soon auction that scores PASS in PASS 1 and also matches a regular search writes two `alerts_log` entries

**File/line:** `ebay_deal_alert.py:3113` (bypass) + `:3318-3320` (`append_alert_log` + `mark_seen` on PASS verdict).

The `is_new` bypass means an ending-soon auction is re-processed even after the regular brand search already handled it. When both copies score a PASS verdict (hard filter: brand-on-pass-list, poly, gender, etc.), the regular search logs and `mark_seen`s it, then the auction lane (which runs last) bypasses `is_new` and logs + `mark_seen`s the *same* item again.

**Concrete scenario:** a `"suit"` auction that matches `"canali suit"` has a gender keyword in its title. Regular search: PASS → `append_alert_log` (`:3318`). Auction lane: bypasses `:3113` → same PASS verdict → second `append_alert_log`. Two `alerts_log.jsonl` rows for one rejected item in one run. Not duplicate *alerts* (PASS = no alert) and not duplicate AI spend (PASS 1 exits before review), just log pollution that the mobile app reads.

**Fix direction:** on the PASS-verdict path (`:3318`), skip `append_alert_log` if the item is ending-soon *and* already seen, or dedupe the auction lane's PASS logging against the raw seen row.

## 5. Low — an auction's transient current-bid is written to the fingerprint `best_price`, poisoning future relist detection

**File/line:** `ebay_deal_alert.py:3124` (fingerprint), `:3824` (written on alert), `:3145` (95% "relist" skip), `:1031-1042` (`upsert_fingerprint` keeps only the minimum).

`total_price` for an auction is the **current bid** + shipping, and `mark_seen(conn, item_id, fingerprint, total_price)` records that as the fingerprint's `best_price`. The fingerprint is `hash(title + seller)` — it deliberately spans listings, not itemIds — and `upsert_fingerprint` only ever lowers `best_price`. So an auction that alerted at a low near-close bid stamps a permanently low "best price" for that title+seller.

**Concrete scenario:** `"hickey freeman suit"` auction alerts at bid $50 (fingerprint best_price $50). The seller later lists another identical suit (same title, same seller, new itemId) as Buy-It-Now at $90. Fingerprint matches; `$90 >= $50*0.95` → skipped as "relist of a previously-seen item at essentially the same price" (`:3145`). The $90 listing is never evaluated — even though $50 was a bid that the user may well have lost, not a real sale price. The 95% tolerance is comparing against a transient auction floor instead of a price the seller actually offered.

**Fix direction:** don't write the auction's current bid into `best_price` (write the fingerprint seen-time only, or a sentinel), so a closing auction's bid can't set a false floor for the seller's future listings.

## Checked and found correct (no bug)

- **`auction-alerted:` key coverage** — there is exactly one `send_alert` call (`:3820`) and the key is checked immediately before it (`:3813`), and set immediately after a successful send (`:3823`). No path alerts without the key being set (a failed `send_alert` correctly leaves it unset so it retries).
- **`mark_seen(conn, key)` with no fingerprint/price** — behaves correctly: `INSERT OR IGNORE` into `seen`, the `DELETE FROM ai_pending` is a harmless no-op on the namespaced key, `if fingerprint:` skips the upsert. The namespaced rows are covered by the same 60-day prune and are only ever read by `is_new`, so they can't collide with or confuse any other consumer of the `seen` table.
- **`ai_pending` corruption from the bypass** — none. Every `mark_seen` deletes the item's `ai_pending` row, and the "no AI price" path preserves aging via `INSERT OR IGNORE`. Repeated in-window processing doesn't duplicate or stall `ai_pending` rows.
- **Downstream assumption that every candidate passed `is_new`** — none found. The dedupe (`:3342`) and priority sort (`:3384`) handle re-entering items correctly; the only leaks are the ones itemized above (comps loss, late duplicate check, PASS double-log).
