403 response-shape evidence
- Across all 145 production 403s in the ten-run sample, the logged header signature was identical: final host `www.ebay.com`, server `AkamaiGHost`, no Via/Proxy-Status, `text/html`, and no x-ebay request/version headers. Body-size distribution: 1,976 bytes x2; 1,977 x17; 1,978 x40; 1,979 x86. The 3-byte spread tracks small query-dependent/error-page variation, not radically different block modes.
- Production logging intentionally excludes body content, so the Actions logs alone cannot establish whether the body contains an `_abck` sensor challenge. It would be false to claim the historical body was “read” from those logs.
- A single bounded local request using this exact module/header path, with **no local proxy configured**, returned HTTP 403 with the same `AkamaiGHost`, `text/html`, and exactly 1,978 bytes. This exact signature/length match makes it strong (not absolute) evidence that the local body is the same response template production receives.
- The local body is an eBay-branded, `noindex,nofollow` HTML page titled `Error Page | eBay`, not the classic tiny Akamai `Access Denied`/`errors.edgesuite.net` body. It contains a script tag but no literal `_abck`, `bm_sz`, “Access Denied”, “Pardon Our Interruption”, CAPTCHA, “challenge”, or “sensor” text.
- Response headers set `bm_s` and `bm_so` cookies for `.ebay.com` and include `x-akamai-transformed: 0 - 0 -`. Cookie values were deliberately not persisted in this log. The `bm_*` names are concrete Bot Manager evidence; the exact role of these two cookies still needs authoritative research before concluding that JavaScript execution is required.

First state-persistence experiment
- Source inspection of installed Scrapling 0.4.15 confirms `Fetcher.get()` uses a `FetcherClient` one-off `CurlSession()` and closes it in `finally` after every call. The production code therefore discards both response cookies and connection state after each search. Scrapling also exposes `FetcherSession`, whose context holds one curl session across requests.
- In one fresh local `FetcherSession` using the exact same headers and no proxy, three same-URL requests produced **403 -> 200 -> 200**. The first response was the same 1,978-byte eBay error template and set only `bm_s`/`bm_so`; the next responses were real 1.27-1.29 MB search-result pages and set normal eBay session cookies plus `bm_s`.
- Visible first-response text was a generic eBay “SORRY / Something went wrong on our end” page with a per-request reference code. Its only script tag was a deferred, randomized same-origin path. No JavaScript was executed by `FetcherSession`, yet request 2 succeeded.
- Given the measured production one-off success rate of only 3/148 (~2.0%), two consecutive successes immediately after one 403 are unlikely under independent random blocking (~0.04% using that empirical rate). This is real evidence that retaining state—not merely waiting or a random header—is relevant locally. A cookie-only replay test is next to separate cookies from TCP/TLS connection reuse.

Cookie-only controlled A/B
- On a different real query, a one-off `Fetcher.get()` returned the matching 1,978-byte 403 and exposed response cookies `bm_s` and `bm_so`.
- Replaying exactly those cookies through a **new** one-off `Fetcher.get()` (fresh curl session/connection) immediately returned HTTP 200 with a 1,802,589-byte real search page containing `s-card` results.
- A third new one-off control request, identical except with no replayed cookies, immediately returned the 1,978-byte HTTP 403 again.
- Sequence: **403 (no cookies) -> 200 (403 cookies replayed) -> 403 (no-cookie control)**. This isolates cookie state from connection reuse and is direct evidence of the actual local blocking mechanism. A JavaScript engine was not needed to mint the accepted cookies: Akamai supplied them on the 403 itself.
- Production applicability caveat: the real residential proxy credential is unavailable locally. If that provider assigns a different exit IP on each connection and Akamai binds `bm_*` state to the exit IP, replay through separate one-off calls may fail there. An immediate retry inside one persistent `FetcherSession` would retain both cookies and the connection/exit and is the most evidence-aligned implementation candidate.

Relying on undocumented legacy `/sch/rss` or `/sch/ajax/` redirect behavior would be less robust than explicitly retaining the challenge cookies with Scrapling's supported `FetcherSession` API.

Implemented change (production verification still unavailable)
- `ebay_scrape.py` now uses Scrapling's public `FetcherSession` instead of stateless `Fetcher.get()` calls. One session is retained per calling thread and proxy configuration, preserving cookies and—where the proxy/server permits—its connection/exit across the sequential scrape searches.
- A retry is narrowly gated: exactly one retry only when the first response is HTTP 403, `Server` identifies Akamai, and the response actually sets `bm_s` or `bm_so`. Generic 403s, 407s, transport failures, and other statuses remain single-attempt failures. A final failed retry closes/discards the session so the next search can get a fresh route.
- The initial challenge is logged at INFO with the same safe response metadata and no cookie values. A final failure still returns `[]` and logs a warning that says the stateful retry was attempted. Transport errors still redact proxy URL/host/user/password.
- Added unit coverage for challenge -> success, challenge -> challenge bounded failure/session close, non-cookie 403 no-retry, cookie values absent from logs, and successful session reuse across different queries. Existing fetch/proxy/header/failure/parser tests were adapted to the session API.
- Focused suite after the edit: `python -m pytest -q test_ebay_scrape.py` -> `23 passed in 0.60s`.
- Real post-change local function check, no configured proxy: first query logged the matching 1,979-byte Akamai cookie challenge, retried in-session, returned HTTP 200 and parsed 63 listings in 1.310 s; the second different query reused the session, returned HTTP 200 without a challenge, and parsed 103 listings in 1.606 s.
- This is much stronger mechanistic evidence than round 1's header-only A/B, but it still does **not** prove the production proxy will accept the state: its credentials/exit behavior are unavailable locally and no commit/push/deployment is authorized. The first deployed Actions run remains the required production test.

Authoritative Akamai context
- Akamai's current Bot Manager reporting documentation says standard web-client telemetry uses first-party cookies to associate/transmit behavior, and explicitly lists `Unknown Bots (Session Validation Failed)` as a possible triggered detection. This aligns with the observed stateless-fail/stateful-pass result without proving eBay's private rule configuration: https://techdocs.akamai.com/security-ctr/docs/dimensions-new
- Akamai's detection-method documentation says transparent detection evaluates request traits including header order/signatures and browser-version mismatches, while active detection uses browser interaction: https://techdocs.akamai.com/cloud-security/docs/detection-methods
- Round 1 addressed one transparent header inconsistency, but round 2's controlled cookie A/B shows session validation is the remaining mechanism for this exact response locally. Akamai also exposes JA4/TLS fingerprint fields in its SIEM data, but the same curl_cffi fingerprint succeeds when state is retained, so TLS fingerprint alone cannot explain this specific local 403.

Final verdict and deployment decision tree
- The remaining blocker is best identified as **Akamai/eBay session-cookie validation**, not a JavaScript-only `_abck` sensor challenge, a TLS fingerprint that can never pass, or a literal hard block of the entire production proxy route. The decisive evidence is the controlled 403/no-cookie -> 200/same-cookies -> 403/no-cookie A/B with otherwise fresh connections, plus successful lightweight session reuse across queries.
- The fresh production rate is still catastrophically bad before this change (145/148 = 97.97% 403), but the three real 200s mean “100% forever / hard ASN block” is not supported. IP/exit reputation can still influence Akamai scoring and cannot be ruled out for the production proxy pool.
- This change is intended to clear the diagnosed block cheaply, and it did so locally against the exact response signature. It is **not claimed production-fixed**: no real proxy credential is available here and no commit/push/deploy was performed.
- On the first deployed run, look for one `retryable Akamai cookie challenge` INFO followed by successful `eBay scrape lane: N extra listing(s)` records. If that happens, later searches should reuse the accepted session without repeated challenge logs.
- If the deployed log shows the retryable challenge and then `after one same-session Akamai-cookie retry` on repeated final 403s, the provider may be changing/losing the exit even inside the session or the production exit is subject to stricter active/reputation checks. Next test a persistent `StealthySession` through that proxy (measured 2.161-2.950 s/search plus 0.858 s startup locally; real-Chrome one-off 6.056 s). The current runner already includes Chrome.
- If a persistent browser through the same proxy also fails, stop request-shape tweaks: the remaining evidence would point to the proxy exit pool/reputation, and the practical fix is a provider/sticky residential session with cleaner exits. Do not add retries that hammer the same denied route.
- If the initial 403 does not classify as retryable in production, extend diagnostics only to log **cookie names**, never cookie values/body/query secrets, before making another behavioral change.
