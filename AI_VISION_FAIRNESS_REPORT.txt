SECTION 1 - WHAT I FOUND IN THE CURRENT CODE (Findings 1 & 2 re-verified)
-------------------------------------------------------------------------

Provider config vs. code design mismatch (the headline):
  - config.json sets "AI_PHOTO_PROVIDER": "gemini" (primary = Gemini).
  - ebay_deal_alert.py's own default and every design comment (line ~429-436,
    ~3146-3153) say DeepSeek is the intended primary since deepseek-v4-flash-
    vision-exp shipped (2026-08-21): "AI_PHOTO_PROVIDER is primary (DeepSeek
    is cheap, no free-tier 429 ceiling)".
  - So production has been running gemini-primary against a codebase built for
    deepseek-primary. Git history: the "gemini" config value predates the
    deepseek-primary switch and has not been touched since.

Call-path facts verified in _call_photo_check() / _call_gemini_json() /
_call_deepseek_json() (all current):
  - Gemini 429 handling: _call_gemini_json() does requests.post(...).raise_
    for_status(), so a 429 raises HTTPError (a RequestException) and
    _call_photo_check() catches it and IMMEDIATELY falls back to DeepSeek.
    There is no retry, no backoff, no 429 accounting anywhere.
  - Both providers are called with the SAME timeout bound: _call_photo_check()
    defaults timeout=20 and passes timeout=_deadline_timeout(hard_stop, 20)
    to whichever provider runs first and again to the fallback.
  - _call_deepseek_json() reserves AI_PAID_VISION_RESERVATION_USD BEFORE the
    network call, so a timeout still costs the paid reservation AND the pool
    slot AND wall-clock. Confirmed at lines 2969-2988.
  - Effective DeepSeek vision timeout in production is 20s (the _call_deepseek
    _json default of 30s is masked because _call_photo_check always passes an
    explicit timeout). Matches the prior investigation's "~20s" figure.
  - Run deadline: hard_stop = run_started + RUN_BUDGET_SECONDS (390s). Each
    call's effective timeout is min(requested, time-remaining-to-hard_stop),
    so near the deadline even a healthy provider gets a sub-20s window.

LIVE PROBE RESULTS (this session, both keys present; direct API calls, no
ledger pollution; small one-off cost ~$0.01 DeepSeek):
  - Gemini text ping: HTTP 200 in 15s and 27s (2 calls). NOT currently 429ing,
    but free-tier latency is 15-27s for a trivial text ping.
  - Gemini 1-photo vision ping: HTTP 200 in 20.1s (payload ~large). That is
    AT the current 20s timeout boundary for a single image.
  - DeepSeek vision, realistic prompt + full JSON schema + 4-image payload:
    4/4 HTTP 200 in 3.5 / 3.5 / 5.5 / 4.5s.
  - DeepSeek text: 200 in 1.3s.

What this means:
  - Finding 1 (Gemini 429s on ~100% of checks) was TRUE in the earlier sample
    window and is well-corroborated by the codebase's own written history
    (sustained multi-hour free-tier 429 dead zones until the ~07:00 UTC daily
    reset). Gemini is NOT 429ing right now, but it has a second, equally fatal
    problem for the primary slot: 15-27s latency vs a 20s timeout. A healthy
    Gemini is frequently abandoned mid-request at the current bound, so the
    check falls back to DeepSeek anyway.
  - Net: under the deployed gemini-primary config, the primary slot provides
    near-zero value in BOTH of Gemini's states - exhausted (429 -> fallback)
    or healthy-but-slow (ReadTimeout at 20s -> fallback) - and in the
    healthy-but-slow state it eats run deadline and SHRINKS the DeepSeek
    fallback's effective timeout (the deadline-squeeze mechanism). This is the
    real root cause of most of the DeepSeek "34% timeouts": DeepSeek itself is
    fast (3.5-5.5s live) but was being invoked late in deadline-starved runs
    as the fallback to a slow primary.
  - Finding 2 (DeepSeek 34% timeouts at ~20s) does NOT reproduce live: healthy
    DeepSeek vision returns in 3.5-5.5s even at the full 4-photo cap. The 34%
    figure was either a DeepSeek incident window or (more likely per the above)
    deadline squeeze caused by gemini-primary. 20s is 4-6x headroom for a
    healthy DeepSeek vision call; it is NOT too aggressive.

Finding 3 and fairness implementation:
  - Confirmed that the shared normal pool previously had no category fairness after
    its urgency/gate/pending/price sort. A golf-equipment burst could take all 12.
  - Added a stable soft-cap scheduler. After six ordinary golf-equipment candidates
    are selected, waiting non-golf candidates are promoted into the initial shared
    window. Golf immediately backfills capacity when fewer non-golf candidates are
    available, so no slot is wasted and golf is never given a hard quota.
  - Ending-soon auctions and isolated Scout/eBay-scrape rows stay in their exact
    positions. Ending-soon rows are exempt from the cap and reduce the ordinary
    window size; the existing reserved-auction slot logic is unchanged. Scout and
    scrape still use only their existing independent counters.
  - This bounded category-specific reservation was chosen over round-robin because
    only golf burst starvation was evidenced. Round-robin would broadly change
    priority semantics across every category after a difficult production night.
